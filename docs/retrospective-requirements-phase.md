# 要件定義フェーズの振り返りとハーネス化の候補

- 作成日: 2026-10-22
- 対象: 2026-10-18〜22 の要件定義・仕様策定（PR #1）
- 目的: この進め方で得た学びを、仕様書 12.2 節のハーネス構築フェーズ（H）の入力にする

## 1. 何をしたか

1. 選択式の質問を 4 問ずつ 4 回（計 16 問）投げ、要件を確定した。各問に推奨案を付けた。
2. 要件定義書と仕様書を書き、PR #1 を作成した。
3. Copilot レビュー 4 件とオーナーのコメント 3 件（Node の LTS、詳細設計フェーズ、ハーネス構築）に対応し、計 5 コミットでマージした。
4. 途中で「pnpm を使う」「cooldown 24 時間」という制約が後出しで追加された。

## 2. 学び

### うまくいったこと

- **推奨付きの選択式質問**は速かった。16 問を 4 往復で終え、推奨案はおおむね採用された。自由記述（「その他」）に書かれた一言「ログを残すのが目的ではなく、項目を残して共有することが目的」が要件の中心になった。選択肢は決定を速め、自由記述は本質を拾う。両方を毎回用意する価値がある。
- **文書を先にリポジトリへ置く**ことで、ワーカーの再起動が複数回あっても作業は失われなかった。状態はチャットではなくファイルと Git に置く。
- **レビュー対応を 1 スレッド 1 コミット**にし、返信にコミット SHA と変更した節を書いた。オーナーは差分だけ見て解決済みにできた。
- **文書にステータス欄**（ドラフト → 確定）を持たせたことで、「確定にしてマージ」という明確な区切りができた。
- **Copilot の自動レビューは文書に対しても有効**だった。4 件はすべて文書内・文書間の整合性の欠陥（複製タイトルの上限超過、FR-41 と編集画面の矛盾、CI 手順と E2E 方針の不一致、M1 の完了条件が範囲内で達成不能）で、人が読み落としやすい種類だった。

### つまずいたこと

- **時間で変わる事実を記憶で書いた**。Node 22 を LTS と書き、オーナーに指摘されて公式のスケジュールで確認したら 22 も 24 も既に Maintenance だった。バージョン・日付・価格の類は、書く時点で一次情報を引き、確認日と出典を残すべきだった。
- **方針系の制約を最初に聞いていなかった**。パッケージマネージャ、供給網対策（cooldown）、Node のバージョン、ホスティングなどは機能要件と独立した「組織の既定値」で、最初の質問に含めるか、リポジトリの約束事として先に置いておけば後出しにならなかった。
- **自己レビューなしで PR を出した**。Copilot が拾った 4 件は、「仕様の各節が要件のどの ID を満たすか」「マイルストーンの完了条件がその範囲だけで達成できるか」「文字数などの制約が派生値（複製タイトル）にも効いているか」を機械的に見れば出す前に気づけた。
- **未送信レビューに返信できなかった**。オーナーのコメントが pending のレビューに入っていたため、スレッド返信が GitHub に拒否され、PR 本体のコメントで代替した。人側は「単発コメントとして送る」か「まとめて送信する」、エージェント側は「拒否されたら PR コメントに退避する」という取り決めが要る。
- **「コメント追加」と人が打つまでエージェントは動かなかった**。PR イベントの購読を使えば、コメントが付いた時点でループが回る。
- **開発プロセスの質問をしていなかった**。「詳細設計フェーズを置く」「ハーネスを作る」はどちらもマイルストーン表へのレビューで出た。フェーズ構成、誰が実装するか、レビュー方針は、機能と同じく最初に聞く項目だった。
