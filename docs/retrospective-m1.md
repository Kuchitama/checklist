## 3. 学び

### うまくいったこと

- **受け入れ基準ごとにテストを先に書き、PR に「基準 ↔ テスト」の表を載せる**。自動レビューの指摘 11 件のうち、受け入れ基準の中の振る舞いに対するものは 1 件（#11）だけで、残りは基準の外（レスポンシブ、アクセシビリティ、時刻の境界、設計の欠陥）だった。受け入れ基準の範囲はテストで守れている。
- **計測で検証する**。Chromium のヘッドレスで `scrollWidth`、要素の矩形、`elementFromPoint`、コントラスト比を測り、修正の前後の数値を返信に書いた。「直した」ではなく「1335px → 360px」で示せるので、レビューの往復が減る。指摘を直す前に必ず再現を測ったことで、誤検知 0 を確かめられた。
- **仕様の不備は同じ PR で直す**（CLAUDE.md 1 章）。7 件の実装 PR のうち 6 件で設計書を直した。設計書のレビューでは見つからず、実装して初めて分かる不備が多い。実装が設計書の最終レビューになっている。
- **1 スレッド 1 コミットと SHA つきの返信**（CLAUDE.md 6 章）は、そのまま機能した。自動レビューのスレッドはエージェントが解決済みにし、人のコメントは返信だけにする分担も問題なかった。
- **回帰テストを 1 箇所壊して確かめる**。#22 の指摘（テストが空振りしていた）を受けて、#26 以降は新しい回帰テストごとに実装を一時的に壊して失敗を確認した。楽観更新のテストなど、通ったように見えて何も検証していないテストを防げる。

### つまずいたこと

- **幅 360px で長い文字列を試していなかった**（#23 のタグ、#26 の説明と項目名。11 件中 3 件）。目視は通常の長さの見本データだけで行い、上限いっぱいの空白のない文字列（タグ 30 文字、URL）を入れていなかった。shadcn の `Badge` は `shrink-0` と `whitespace-nowrap` を持ち、flex の子は `min-w-0` がないと内容の最小幅より縮まない。どちらも見本データでは出ない。
- **shadcn の既定値が NFR-03 と画面設計書 2.2 節を満たさない**（#23 のタップ領域とコントラスト）。`Button` は 32〜36px、`--success` の既定色は白で 3.3:1 だった。生成した部品をそのまま使わず、44px と 4.5:1 を測る必要がある。
- **時刻の境界を落とした**（#21 の `Date.UTC` の 0〜99 年、#26 の日付変更）。「存在しない日付」や「今日」のテストは書いたが、境界（100 年未満、0 時、画面を開いたままの日またぎ）は書いていなかった。
- **設計書のアルゴリズムに欠陥があり、そのまま実装した**（#26 の高、画面設計書 5.4 節）。一時状態を「書き込みの完了時」に捨てる手順は、完了の通知が購読の更新より先に届く順序を考えていなかった。設計書どおりに書いたことは正しさの根拠にならない。イベントの順序（書き込みの完了と購読の更新の前後、連打）を列挙し、順序ごとにテストを書いてから信じるべきだった。
- **Issue の「対象外」に書かれた義務を見落とした**（#23。「本 Issue ではルートの定義だけを置く」）。受け入れ基準だけを読んで作業し、「対象外」の中の「〜だけを置く」を飛ばした。義務は対象外ではなく受け入れ基準に書くべきで、読む側も対象外を義務の有無で読む必要がある。
- **テストが空振りしていた**（#22）。リセットの前に `toggleItem` を呼んでいたため、`resetChecklist` が `updatedAt` を更新しなくても通った。前提を作る操作が検証対象の値を先に作ってしまう形は避ける。
- **PR を積んだ**（#22 を #21 の上に）。squash マージ後にベースを `main` に切り替えると、同じ内容の箇所で見かけ上のコンフリクトになり、`main` が #21 の最終コミットと同じことを確かめてから積んだ側を採る手順が要った。積まずに順番に出す方が安い。
