# 秘密情報・個人情報の取り扱い

- 作成日: 2026-10-23
- ステータス: 確定（2026-10-23 レビュー完了）
- 関連文書: [CLAUDE.md](../CLAUDE.md)（10 章）、[要件定義書](./requirements.md)（NFR-07）

このリポジトリは公開（public）で運用する。公開後は、誤って入れた情報を完全に取り消す手段がない（フォーク、キャッシュ、クローンに残る）。本書は「何を入れてはいけないか」「入れないための仕組み」「入ってしまったときの手順」を定める。

## 1. リポジトリに入れてはいけないもの

| 種類 | 例 | 代わりにどうするか |
| --- | --- | --- |
| 認証情報 | API キー、トークン、パスワード、秘密鍵（`.pem`、`.key`）、証明書、接続文字列、Webhook URL | 本アプリに置き場所はない。静的サイトではビルド時の環境変数や GitHub Secrets の値も成果物に埋め込まれ、GitHub Pages から誰でも取得できるため、クライアントコード・ビルド成果物・CI の環境変数のいずれにも入れない。認証情報が必要な機能は、仕様書を更新してサーバー側に保管する設計にしてから着手する |
| 個人情報 | 電話番号、住所、本名（GitHub のハンドル名以外）、第三者のメールアドレス | 連絡先は GitHub のプロフィールに委ねる。オーナー自身の GitHub アカウントに登録したメールアドレスがコミットの author に入るのは秘匿対象外（オーナーの判断、2026-10-23） |
| 内部情報 | 社内のホスト名、内部 URL、IP アドレス、社内システム名、顧客名 | 例示には `example.com`、`192.0.2.0/24`（文書用に予約された値）を使う |
| 実データ | 実在の人物や業務のチェックリスト、本番 DB の書き出し | テストデータはデータ設計書 7 章の固定データを使い、架空の内容にする |
| 一時ファイル | `.env`、`.npmrc`（トークンを含みうる）、IDE のローカル設定、ログ | `.gitignore` に入れてある。ローカル専用の設定が必要になった場合も、値を空にした `.env.example` だけを置き、秘密の値は書かない |

本アプリは設計上、サーバーも外部 API も使わない（要件 NFR-07）。したがって通常の開発で認証情報が必要になることはない。必要になった時点で、まず仕様書を更新して理由を記す。

## 2. 入れないための仕組み

| 層 | 仕組み | 状態 |
| --- | --- | --- |
| 書く前 | CLAUDE.md 10 章の規則。PR を出す前の自己チェック項目 | 導入済み |
| コミット時 | `.gitignore` で `.env*`、鍵ファイル、`.npmrc`、`.netrc` を除外 | 導入済み |
| push 時 | GitHub の **Push protection**（公開リポジトリでは無料）。既知の形式のトークンを含む push を拒否する | リポジトリ設定 → Code security → Secret scanning → Push protection を有効にする（オーナーの操作） |
| PR / 日次 | `secret-scan.yml`（gitleaks）。全履歴を対象に PR と push で実行し、毎日 1 回ルール更新分を再検査する | 導入済み。ブランチ保護で必須チェックにする（オーナーの操作） |
| 常時 | GitHub の **Secret scanning**（公開リポジトリでは無料）。GitHub 側で検出した既知のトークンを通知し、発行元に失効を依頼する | リポジトリ設定で有効にする（オーナーの操作） |
| 身元 | コミットの author にはオーナー自身の GitHub アカウントのメールアドレスか GitHub の noreply アドレスだけを使う。第三者のアドレスを author / Co-Authored-By に書かない | 運用中 |

gitleaks の除外は `.gitleaks.toml` に理由つきで書く。検出を「誤検知」として除外するときは、PR 本文にその判断を書く。

## 3. 入ってしまったときの手順

1. **失効させる**。履歴から消す前に、漏れた鍵やトークンを発行元で無効化し、新しいものに替える。公開リポジトリに一度でも push した秘密情報は、消しても漏れたものとして扱う。
2. **取り除く**。現在のブランチから該当箇所を削除し、`.gitignore` や gitleaks の設定で再発を防ぐ。
3. **履歴の扱いを決める**。個人情報など失効できない情報は、オーナーが履歴の書き換え（`git filter-repo`）を判断する。書き換えは全員のクローンに影響するため、オーナー以外は行わない。
4. **記録する**。本書 4 章の監査記録に、日付・内容・対処を追記する。
